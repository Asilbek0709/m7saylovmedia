# Резервные копии и «пульс» базы

Бесплатный проект Supabase имеет две особенности:

1. **Засыпает** после 7 дней без запросов к базе — сайт перестаёт работать,
   пока проект не запустят вручную в панели Supabase.
2. **Не делает резервных копий** — удалённые или испорченные данные не вернуть.

Обе закрыты бесплатно:

| Что | Где | Как часто |
|---|---|---|
| Пульс: запрос к базе | Vercel Cron → `/api/keep-alive` | каждый день, 08:00 по Ташкенту |
| Резервная копия | GitHub Actions → «Резервная копия базы» | каждое воскресенье, 07:00 по Ташкенту, хранится 90 дней |

---

## 1. Пульс (настраивать ничего не нужно)

Расписание лежит в `vercel.json` и включается само после деплоя.
Проверить: Vercel → проект → **Settings → Cron Jobs** — там должна быть
строка `/api/keep-alive`. Там же кнопка **Run** для ручного запуска.

Необязательно: чтобы адрес не мог дёргать кто угодно, добавьте в Vercel
(Settings → Environment Variables) переменную `CRON_SECRET` — любую длинную
случайную строку — и сделайте Redeploy. Vercel сам подставит её в запросы
расписания, остальным адрес ответит 401.

## 2. Резервная копия — настройка один раз

### Шаг 1. Строка подключения к базе

1. Supabase → проект → кнопка **Connect** (вверху).
2. Вкладка **Connection string**, тип **URI**, способ **Session pooler**
   (не «Direct connection»: прямое подключение работает только по IPv6,
   а у GitHub его нет).
3. Скопируйте строку вида
   `postgresql://postgres.<id>:[YOUR-PASSWORD]@aws-0-<регион>.pooler.supabase.com:5432/postgres`
   и вставьте вместо `[YOUR-PASSWORD]` пароль базы (Supabase → Project Settings →
   Database → Database password; если не помните — там же «Reset»).
   Если в пароле есть символы `@ : / ? # %`, их нужно закодировать
   (`@` → `%40`, `#` → `%23` и т. д.) — проще задать пароль из букв и цифр.

### Шаг 2. Пароль шифрования

Придумайте длинный пароль (от 16 символов) и **сохраните его отдельно от
GitHub** — в менеджере паролей или на бумаге. Без него копию не расшифровать
никому, включая вас.

### Шаг 3. Секреты в GitHub

GitHub → репозиторий → **Settings → Secrets and variables → Actions →
New repository secret**, два секрета:

| Имя | Значение |
|---|---|
| `SUPABASE_DB_URL` | строка из шага 1 |
| `BACKUP_PASSPHRASE` | пароль из шага 2 |

### Шаг 4. Первый запуск вручную

GitHub → **Actions → «Резервная копия базы» → Run workflow**. Через 1–2 минуты
запуск станет зелёным, а на его странице будет таблица «сколько строк в каждой
таблице» и файл `ms7-backup-ГГГГ-ММ-ДД` внизу, в разделе **Artifacts**.

Если запуск красный — откройте его: сообщение об ошибке подскажет, что не так
(чаще всего — неверный пароль в строке подключения).

## 3. Как достать данные из копии

1. GitHub → Actions → нужный запуск → **Artifacts** → скачать
   `ms7-backup-ГГГГ-ММ-ДД` (придёт ZIP, внутри файл `.tar.gz.gpg`).
2. Распакуйте ZIP. Откройте **Git Bash** в этой папке
   (правый клик → «Open Git Bash here») и выполните:

   ```bash
   gpg -d ms7-backup-ГГГГ-ММ-ДД.tar.gz.gpg | tar -xzf -
   ```

   gpg спросит пароль шифрования. Появятся файлы:

   | Файл | Что внутри |
   |---|---|
   | `public.sql` | все таблицы сайта с данными, функции, триггеры, правила доступа |
   | `auth-users.sql` | учётные записи (почта, хэш пароля) |
   | `summary.txt` | сколько строк было в каждой таблице |

Это обычные текстовые SQL-файлы: их можно открыть в блокноте и найти нужную
оценку или издание.

## 4. Восстановление

**Пропало несколько записей** (например, по ошибке удалили издание с оценками).
Найдите в `public.sql` блок `COPY public.<таблица> ... FROM stdin;`, возьмите
нужные строки и верните их через Supabase → SQL Editor. Если сложно —
пришлите файл разработчику.

**Проект Supabase удалён или испорчен целиком.**

1. Создайте новый проект Supabase.
2. Сначала учётные записи, потом сайт (нужен `psql` — проще всего выполнить
   с компьютера разработчика):

   ```bash
   psql "<строка подключения нового проекта>" -f auth-users.sql
   psql "<строка подключения нового проекта>" -f public.sql
   ```

   Сообщения вида «schema "public" already exists» — нормальны.
   Затем в SQL Editor нового проекта верните триггер, который создаёт профиль
   при регистрации (он висит на `auth.users` и в копию схемы public не входит):

   ```sql
   create trigger on_auth_user_created
     after insert on auth.users
     for each row execute function public.handle_new_user();
   ```

3. В Vercel замените `NEXT_PUBLIC_SUPABASE_URL` и
   `NEXT_PUBLIC_SUPABASE_ANON_KEY` на значения нового проекта и сделайте Redeploy.
4. В новом проекте заново настройте Authentication → URL Configuration,
   шаблоны писем и SMTP (как в первый раз).

## Важно знать

- **Копии хранятся 90 дней**, то есть в любой момент есть ~12 последних
  недель. Важную копию (например, после закрытия тура) скачайте и сохраните
  у себя — она не исчезнет.
- **GitHub отключает расписание**, если в репозитории 60 дней не было
  коммитов, и присылает об этом письмо. Тогда откройте Actions → «Резервная
  копия базы» → **Enable workflow**. Пульс от этого не зависит — он в Vercel.
- **Смена пароля базы** в Supabase ломает бэкап: обновите секрет
  `SUPABASE_DB_URL`.
